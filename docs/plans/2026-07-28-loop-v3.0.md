# Plan: feature-loop v3.0 — "ticket in, status out"

Make the loop start from a Jira ticket and end at a written-back ticket status — and stop
writing its own telemetry into the user's repo.

## What changes (summary)

- **The loop's memory is removed.** The blind-spot ledger (`docs/reviews/blind-spots.md`) and the
  metrics journal (`docs/loops/metrics.jsonl`) were committed onto every feature branch, which
  put loop telemetry in the diff that gets shipped to the paid external reviewers. `/loop-stats`
  goes with them; it had no other data source. `docs/plans/` and `docs/landing.md` stay.
- **`/ship-feature PROJ-123`** reads the whole ticket, plans, builds, reviews, resolves
  conflicts, merges, and writes back — autonomously by default.
- **`/ticket-intake`** (new) turns a Jira issue into numbered requirements, each with a verbatim
  quote and its source, reconciling comments against the description chronologically so a
  scope-changing comment wins and the requirement it replaced is shown struck through.
- **`/resolve-conflicts`** (new) integrates a moved target branch. Merge, not rebase, so review
  threads stay anchored. Conflicts are classified before they're touched, and three classes have
  no safe automatic method at all.
- **`/ticket-report`** (new) posts one comment — plan, per-requirement coverage with evidence,
  and explicitly what the ticket asked for that was *not* built — then transitions the ticket.
  Partial coverage never lands in Done.
- **The requirement chain** runs REQ ids through intake → plan → build → report, with a mandatory
  residue block for source text that produced no requirement, because that is the only place an
  omission can become visible.
- **Two latent bugs fixed**: the convergence check read a stale pipeline status as green (GitLab
  hasn't created the new commit's pipeline yet when you poll right after a push), and
  `/build-feature` Step 2 silently created a divergent branch when the remote branch already
  existed.

## Risks

- **Autonomy erasing the deciders.** Six hard stops used to end in a human. Mitigated by the
  autonomy contract: "ask the user" becomes "stop and hand off with evidence", never "decide it
  yourself" — an agent told both to run autonomously and to stop and ask would otherwise resolve
  that by proceeding.
- **Ticket text is untrusted input** from a much wider set of people than can merge code, and it
  reached reviewers through two channels (the context pack and the MR description). Mitigated by
  the capability envelope, the provenance split, and the snapshot freeze.
- **Coverage that is 100% by construction** — the same model extracts, implements and grades.
  Mitigated by verbatim quotes, the residue block, and evidence-or-downgrade; coverage is
  reported as two numbers so the second can see an omission.
- **MCP is OAuth-only**, so ticket mode cannot run headless. Accepted deliberately; the failure
  mode that mattered was improvisation, so unavailability is a hard stop that forbids inferring
  a ticket's contents.
- **Auto-resolved conflicts silently reverting the target's work.** Mitigated by the target-work
  check — the highest-value verification in the conflict skill.
- **Transitions vary per project and per current status.** Read from the live workflow at write
  time; no committed mapping file, since that would reintroduce repo memory.

## Deferred

REST + token transport for headless ticket runs; other trackers (Linear, GitHub Issues); Done
gated on `/land` rather than the merge (available today via `JIRA_STATUS_DONE`); parallel
worktrees for concurrent tickets — ticket mode takes a `.loop/lock` and refuses instead.
